# v003: distribute 128-column S8 tile across four 64-thread waves

Starting branch: codex-power, parent commit c875fcaff. The candidate is assembled from the user's ffa68b684e3876df2821fe34c9959493c2ca065a original submission plus the independent v001 one-pass S8 math. No earlier optimized NSA kernel is imported or copied. Machine: sc-16g-2 / C500 16G sGPU.

Observed evidence: the correct one-pass 128-token tile with threads=64 took 674.616 us versus v000 124.155 us. Its generated device C++ assigned 32 FP32 scores per thread and retained 4x8 QK plus 8x4 PV MFMA loops. MXCC reported 109 MT/56 ST registers and staticMaxWarps/PEU=4. Grouping four blocks with the same 64-thread CTA also failed at 242.396 us and 150 MT/30 ST registers. These data suggest work distribution and fragment pressure, not simply the number of Python-level T.gemm calls, limit the current design.

Hypothesis: raising the one-pass CTA from 64 to 256 threads will distribute the 128 sparse positions across four waves, reduce score fragment and MFMA work per thread, and lower case12 latency. Predicted generated code has fewer than 32 scores per thread and fewer sequential MFMA iterations per thread. Falsifiers: compiler repeats work in every wave, per-thread registers remain excessive, any correctness failure, or end-to-end case12 latency remains above the original 124.155 us baseline. CTA/shared occupancy and barriers are risks.

The exact source must use only the user's three import statements. No helper class, async copy, foreign code, or Torch kernel computation. First screen the original case12 reference; only a promising candidate proceeds to full 14-case official and profile evidence.

Outcome: The first 256-thread candidate failed TileLang layout inference between the FP32 scores and FP16 scores_half fragments. Its exact source and compiler log are preserved. Moving scores_half into shared made the same four-wave design compile and pass the case12 reference. Generated device code then used eight FP32 scores per thread versus 32 in v001, and MXCC reported 54 MT/28 ST, staticMaxWarps/PEU=8. Nevertheless the target screen was 338.908 us versus v000 124.155 us, and generated code had nine static CTA sync sites. The predicted resource change occurred; the predicted latency change did not. Stop this design and re-profile the baseline before a different mechanism.
