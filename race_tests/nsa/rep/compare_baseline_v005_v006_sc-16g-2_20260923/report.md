## 波动来源判断

v006 的 case 4、5、7、8 走原版 QK 路径；与 baseline 对应 case 的生成 **device 和 host 源码均逐字一致**，但计时依然不同。例如 case 4 的 v006 三轮为 `0.016333/0.023747/0.023869 ms`，而 baseline 为 `0.016589/0.016128/0.017111 ms`。这说明端到端 `run_kernel` 计时除了设备 kernel 本身，还受到运行时状态、Python 调用间隔或调度等因素影响；仅凭本次数据不能定位唯一来源。

`mx-smi` 每 5 秒采样中，XCORE 多数在活跃时为 1125 MHz，空闲时为 428 MHz；第三次 baseline 期间有一次 685 MHz。采样粒度不足以把这一点直接归因到 case 7 的毫秒级异常。进程列在部分测试期间甚至显示 `no process found`，不能据此排除其他负载或调度影响。

**结论：原始测量存在显著运行时波动；先前依据单轮数据宣称逐 case 提升，是统计解释上的错误，不是 CSV 数字抄错或平均公式算错。** v005/v006 的中位数呈现收益迹象，但若要决定正式分流边界，还需要在更稳定的运行窗口做更多交错复测，并同时关注未改动的对照 case。
